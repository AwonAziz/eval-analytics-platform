# eval-analytics-platform

A SQL-backed evaluation and telemetry analytics platform: an ELT warehouse over
the run artifacts your ML projects already produce, with real schema
migrations, ingestion validation, a SQL API, a BI dashboard, and the
analytical queries that answer real questions about model quality.

**Stack** DuckDB · SQLAlchemy · Pandas · Pydantic · FastAPI · Streamlit/Plotly · GitHub Actions

---

## What this is actually for

The point is not the table layout. It is that six questions about model
quality are hard to answer from a notebook and trivial once the data is in a
warehouse:

| Question | Where it lives |
|---|---|
| LoRA vs full fine-tune — paired delta, bootstrap CI, McNemar p, per class | `analysis/lora-vs-full` |
| Calibration by arm across confidence buckets — *why* ECE is 0.018 vs 0.031 | `analysis/calibration` |
| INT8 vs FP32 — p50/p99 latency, size, prediction-agreement rate | `analysis/quantisation` |
| Drift trend per feature over time on PSI/KS/JS | `analysis/drift` |
| Error rate by document-length bucket — the 17–32 token finding | `analysis/length-buckets` |
| Which slices LoRA still loses on, and by how much | `analysis/slice-losses` |

## Provenance: read this first

The warehouse has two kinds of rows and **labels every one of them** with a
`data_origin` column. A fresh clone has only the synthetic rows — the measured
rows appear when the upstream telemetry database is present. Nothing is
silently mixed.

**`synthetic`** — generated by `ingest/artifacts.py` from a fixed seed. The
fine-tuning project that owns `test_preds.npy` / `serving_report.json` is a
separate repository, so that module fabricates artifacts of exactly those
shapes and writes them to `data/raw/generated/`. `eap build` regenerates them
byte-for-byte, which is why they are not committed.

**`real`** — genuinely measured, and only present when the upstream
`llm-drift-monitor` telemetry database is found. It supplies 5,140 per-request
predictions (gold label, predicted label, confidence, timestamp) and 1,596
drift/quality metrics. All 5,140 carry the request text, so document-length
buckets are derived from real text; 2,762 carry a gold label; and 2,378 are
unlabeled production traffic, kept with a NULL label rather than discarded or
guessed at. Point `EAP_TELEMETRY_DB_PATH` at any SQLite database with that
shape, or set it empty to disable.

The ingest layer does not know the difference. It lands and validates whatever
is on disk, so **dropping in the real fine-tune artifacts replaces the
synthetic ones with no code change.** Filter any figure to
`data_origin = 'real'` to see only measured numbers.

The synthetic generator is not noise. It encodes specific, explainable findings
so the queries have something real to find:

- LoRA is better *calibrated*, full fine-tune better *separated* — each arm
  gets its own logit scale and its own residual overconfidence, so accuracy
  and ECE move in opposite directions.
- Full fine-tune carries a majority-class prior, so it wins the 5 head classes
  and loses the 3 tail classes. LoRA uses 1.35% of the trainable parameters.
- Documents in the 17–32 token band contain a single ambiguous cue term, so a
  paired label is pulled in. That is the sole driver of the length error spike,
  and it lands ~4x above the neighbouring buckets rather than being part of a
  smooth length gradient.

make install      # venv + project
make build        # generate artifacts, rebuild warehouse, run quality gate
make summary      # row counts and provenance

## The star schema

```
dim_model         arm, method, adapter rank, trainable vs total params, quantisation
dim_experiment    hypothesis, owner, status
dim_feature       drift-tracked feature, numeric vs categorical, source system
dim_slice         overall | class | length_bucket | drift_window
dim_date          year, quarter, month, ISO week, weekday, weekend

fact_evaluation_run     one row per (experiment, model, slice, date, window)
                        accuracy + CI bounds, macro F1, ECE, MCE, Brier, trainable params
fact_prediction         one row per (evaluation run, example)
                        per-class probabilities, max probability, margin, entropy,
                        correctness, token count, length bucket, regime
fact_serving_request    one row per timed request under a quantisation config
                        latency, batch size, input tokens, model size, peak memory
fact_drift_measurement  one row per (feature, window, metric)
                        PSI / KS / JS pivoted, thresholds, severity
```

`fact_evaluation_run`'s grain includes `window_id` because one run evaluates
many windows that can share a date *and* a regime label — two `baseline`
windows in one day are genuinely different evaluations.

### Two views that carry the analytical work

- **`v_model_quality_headline`** — headline metrics on the `overall` slice.
- **`v_prediction_slice`** — projects every prediction onto all the slices it
  belongs to at once (its class, its length bucket, its drift regime, overall).
  This is what makes "how did each arm do on every slice" one query instead of
  a `UNION` per slice family.
- **`v_drift_pivot`** — one row per (feature, window) with PSI/KS/JS side by side.

## ELT and validation

```
data/raw/generated/*.npy,*.json   +   telemetry.db
        |
   extract        reshape bytes -> staging records; derive token counts, entropy
        |
   land           stg_*_raw, every column nullable text so a bad row survives
        |
   validate       Pydantic contracts; rejected rows -> ingestion_rejection
        |
   transform      conform dimensions, derive surrogate keys, project slices
        |
   load           typed marts + mart_freshness
```

Rejected rows are **counted, not tolerated**. `ingestion_rejection` records each
one with its machine-readable error codes and the raw payload. Contracts are
strict about unknown keys, so a renamed upstream column fails loudly rather
than passing silently.

Bounds are mostly physical rather than statistical: confidence in `[0, 1]`,
latency non-negative, `n_correct <= n_samples`, accuracy inside its own
confidence interval, `trainable_params <= total_params`.

The default build must produce **zero** rejections and CI fails if it does not.
The rejection path itself is exercised by tests against deliberately corrupted
artifacts, so the mechanism is proven without polluting the default build.

### Migrations

Plain SQL in `src/eval_analytics/warehouse/migrations/`, applied in version
order, each inside its own transaction, with the applied checksum recorded in
`schema_migrations`. Running `eap migrate` again is a no-op; **editing a file
that has already been applied raises** rather than letting the warehouse drift
away from what CI built. Schema changes go in a new `V006__...sql`.

## The quality gate

`eap check` is what CI runs. It fails on any of:

1. **`validation_rejections`** — any rejected row (limit 0 by default).
2. **`referential_integrity`** — an orphaned fact row, or a dimension member no
   fact references.
3. **`mart_freshness`** — an empty mart, or a mart lagging the newest record in
   **its own staging table**. Deliberately not a global frontier: drift
   measurements legitimately extend past the evaluation date, and comparing
   every mart to the newest date in the warehouse would flag a complete build
   as stale.
4. **`last_ingestion_run`** — the most recent pipeline run did not succeed.
5. **`analytical_coverage`** — fewer than 2 arms, fewer than 2 quantisations, a
   missing slice family, no drift features, too few labelled predictions, or
   fewer than 2 classes. Without these the six analyses would be quietly
   meaningless.

Surrogate keys are BLAKE2b over each row's natural grain, not DuckDB's
`hash()`, so rebuilding from identical inputs yields identical keys and a diff
of the warehouse is a meaningful review artifact.

## Findings the warehouse produces

From the current build (`eap report <name>`):

**LoRA vs full fine-tune** — paired on 2,400 shared documents. Full fine-tune
leads by **4.13 points** (0.9558 vs 0.9146), paired bootstrap 95% CI
`[-0.0500, -0.0329]`, exact McNemar **p ≈ 1e-22**. But it wins 5 head classes
and loses all 3 tail classes, while training **74x more parameters** for the
2.1% ECE degradation and the tail collapse.

**Calibration** — ECE **0.0180** (LoRA) vs **0.0307** (full fine-tune). The
decomposition shows where each comes from: full fine-tune puts 1,735 of 2,400
examples in the 0.93–1.00 bin at 99.5% accuracy, so its error is concentrated
in the confident-but-wrong tail, whereas LoRA's error sits in the mid-confidence
band where it under-states confidence.

**Quantisation** — INT8 is **3.20x** faster at p50, **3.40x** at p99, and
**3.85x** smaller (66.0 MB → 17.2 MB), at **99.92%** prediction agreement
(2 disagreements in 2,400). The INT8 build rounds pre-softmax activations onto
a symmetric per-class grid in groups of 32 rows; a single per-tensor scale
would flip ~5% of predictions, several times worse than any real INT8
deployment.

**Length buckets** — the **17–32** bucket is the finding: LoRA's error rate
there is **0.288 against 0.072 and 0.024** in the neighbouring buckets, a
**6.0x lift**. The neighbouring buckets are near-flat, so the spike is not a
length effect. It is concentrated on four label pairs (`invoice`→`financial_report`
29.6% of the bucket's errors, then `contract`→`legal_filing`,
`resume`→`technical_manual`, `scientific_paper`→`medical_record`).

**Slice losses** — 14 measured slices, 11 losses, 10 of them significant. The
worst is 17–32 at **-12.88 points**; then `resume` -7.51 and `invoice` -6.71.
LoRA's 3 wins are the tail classes, none individually significant — which is
the honest reading, not a LoRA win.

## API

Read-only over the warehouse. Every analytical function is an endpoint returning
the same structures the CLI prints.

```
GET  /health                       GET  /analysis/lora-vs-full
GET  /meta/dimensions              GET  /analysis/calibration
GET  /meta/arms                    GET  /analysis/quantisation
GET  /meta/summary                 GET  /analysis/drift
GET  /meta/quality-gate            GET  /analysis/length-buckets
GET  /query/runs                   GET  /analysis/slice-losses
POST /sql                          (single read-only SELECT/WITH, row-capped)
```

`/sql` is restricted rather than trusted: single statement, must start with
`SELECT`/`WITH`, write and DDL keywords rejected, row cap enforced. 15 blocked
statements are asserted in the test suite.

## Dashboard

`streamlit run dashboard/app.py` — seven views, 17 live Plotly charts, reading
the DuckDB file directly with no HTTP hop. Sidebar selects the arm pair,
quantisation, bootstrap resamples and calibration bin count.

Rendering every view headlessly through Streamlit's `AppTest` is part of the
test suite, so a broken chart fails CI instead of waiting to be discovered.

The dashboard keeps the real end-to-end telemetry latency on its own scale
behind an expander: it measures whole-application latency including retrieval
and response assembly, so it is not comparable to the model-only benchmark and
would flatten that comparison if plotted on one axis.

141 tests, hermetic by default — the suite does not require the upstream
telemetry database, so it passes on a clean checkout with no external

that database is absent.

## Known limits

- The fine-tune artifacts are generated, not measured. Real numbers replace them
  by dropping files into `data/raw/` — see *Provenance* above.
- INT8 quantisation is approximated by rounding pre-softmax activations onto a
  group-wise symmetric grid. It reproduces realistic disagreement rates; it is
  not a simulation of a particular kernel.
- Bootstrap intervals resample documents, which is the right unit for paired
  comparisons but does not capture variance across training runs. A single
  training run per arm is modelled.
